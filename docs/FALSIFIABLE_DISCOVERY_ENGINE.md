# Thalos Prime: Falsifiable Discovery Engine

## Purpose

This is the first executable product layer for the Thalos X principle: change representations, transfer a structural pattern, write down what it predicts, and specify what result would disprove it. It complements existing search, graph, symbolic-constraint and runtime components. It does not claim to solve general scientific discovery.

## What it does now

- Represents claims with a domain, assumptions, provenance-bearing evidence, and optional canonical proposition keys.
- Finds explicit conflicts when claims share a proposition key and have opposite polarity.
- Selects candidate cross-domain patterns using transparent phrase matches.
- Returns a chosen representation, proposed invariant, prediction, falsifier and test plan for each candidate.
- Evaluates a closed set of scalar constraints without executing user-supplied code.
- Links observations to stable hypothesis IDs and labels them supported, refuted, contested or inconclusive according to submitted outcomes.
- Produces deterministic report IDs from the supplied inputs and preserves limitations and missing information.

## What it does not claim

A keyword match is not semantic understanding. An analogy is not evidence. A supplied observation is not independently authenticated by this module. The label supported means only that the submitted observation is consistent with the candidate, not that truth has been established. A satisfied constraint verifies only that declarative condition against the values supplied. This release does not search all prior literature, execute arbitrary proposed code, reproduce physical experiments, or establish novelty.

## Local use

    pip install -e ".[dev]"
    python -m thalos_prime.discovery.cli "System throughput is slow because of a capacity bottleneck"
    python -m thalos_prime.discovery.cli --input examples/discovery_problem.json --output report.json
    pytest tests/test_discovery_engine.py tests/test_api_discovery.py -q

The CLI emits JSON so reports can be stored, compared between runs, reviewed, and passed to later verification modules.

## API contract

The route is registered by the main application at POST /api/v1/discovery/analyze. Send a question and optionally structured claims, constraints, values, observations, and max_hypotheses. The response includes report_id, representation choices, candidate hypotheses, contradiction pairs, constraint outcomes, missing-information notes and limitations.

## Evidence lifecycle

1. Candidate: generated by the pattern library; not tested.
2. Supported or refuted: a declared observation was linked to it. The report retains its source and method but does not independently authenticate it.
3. Contested: both supporting and refuting observations exist.
4. Inconclusive: the submitted observation did not discriminate the candidate.

A production verifier should promote claims only after reproducing tests in an isolated environment or checking a formal proof, preserve test inputs and output hashes, and compare against independently defined baselines. Automated deployment should remain separate from hypothesis evaluation.

## Acceptance criteria for the next milestones

- Retrieval connectors return source snippets, dates, and provenance instead of unattributed assertions.
- Representation selection is benchmarked against fixed baselines on problems not used to author the patterns.
- Every candidate has a discriminating experiment, formal obligation, or counterexample search.
- Evaluation includes negative controls and adversarial cases, not only examples that favor the system.
- Hypothesis scores are calibrated against external ground truth; lexical coherence is not used as a proxy for truth.
- Results are versioned and reproducible, and a failed test leaves the prior stable implementation intact.
